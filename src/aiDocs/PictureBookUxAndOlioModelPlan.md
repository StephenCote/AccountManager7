## Part B — What the workflow IS vs. what was expected

**As built.** The graph (`olio.pb.workflow/node/binding/artifact/run`) is a **render-provenance DAG**. Rows are written only by `generateSceneImage :8269` → `PbPipelineUtil.openSceneGraph :203` (find-only, swallows failure). Node types are all render stages (`PbNodeTypeEnumType`: SCENE_PROMPT, PORTRAIT, LANDSCAPE, REFERENCE_STRIP, COMPOSITE, SCENE; STYLE_BIBLE never created). Edges are input dependencies (`ROLE_*`, `PbPipelineUtil :76-87`). Status is a hash comparison (`recomputeStatus :543`). Extraction and `createFromScenes` write **no** graph rows and **no** `olio.pb.scene` rows. Live: 1 of 232 books has a graph; 30/31 of the shared user's books return the no-workflow shape. So the canvas is empty for almost every book, and when it is not, it shows render internals for the 2 scenes rendered, not the story.

**Why it cannot be the "sequential revelation" view as built.** Story order lives in the PB1 meta `scenes[]` and note `index`, not in the graph; characters are `character` bindings by `refObjectId` with no `sourceNode`, so they are never drawn; there is no chapter, cast, next/previous, or event node. Making STALE/DONE mean anything for a story beat would overload a render-status vocabulary.

**The root defect is the dual representation.** PB1 (`~/Data/PictureBooks/<slug>/{.pictureBookMeta, Scenes/*.note}`, user-owned, ephemeral models) and PB2 (`olio.pb.*` under the world, olio-owned) hold the same scenes; PB2 scene rows are created lazily at render and matched to PB1 by position, so a PB1 reorder desyncs them; `/settings` used the PB1-only resolver; the viewer title is missing for PB2 ids. `PictureBook2Plan.md` §2.2 intended `olio.pb.scene` to replace the per-scene note and reorder to be N `sceneIndex` patches (`sceneModel.json:16` still says so). That was never realised.

### Options

| | B1 Provenance graph + separate Story view | B2 Extend the graph (SCENE/CHARACTER/CHAPTER nodes at extraction) | B3 Hybrid |
|---|---|---|---|
| Graph | Unchanged; stays a render DAG | Becomes the story record; new non-executable node types; ordering edges | Unchanged |
| Story record | `olio.pb.scene` created at extraction; `characters` participation written; `sceneIndex` is order | Node rows | `olio.pb.scene` as in B1; canvas gains a read-only "story lane" drawn from `/scenes` |
| Cost | M backend (create rows in `createFromScenes`, migrate notes), M UI | L; overloads status semantics; every graph util must skip non-render nodes | B1 + S |
| Risk | Two representations until PB1 retired | Graph becomes the thing nobody can use, only bigger | Same as B1 |

**Recommendation: B3 built on B1.** Make `olio.pb.scene` the primary scene record: (1) `createFromScenes :7904` creates one row per scene via `PbBookUtil.createScene :641` and writes `characters` (`pb.scene.character`), keeping the note as a derived dual-write during transition; (2) `getCreateSceneRow :292` becomes a find; (3) `listScenes :9798` reads rows (fall back to notes for legacy books); (4) `PUT /scenes/order` calls `PbBookUtil.reorderScenes :714` (N patches — already used by ChapBook); (5) **[R2]** a new **scenes-only backfill into the existing `olio.pb.book`** for the 8,586 existing notes — `PbSceneUtil.backfillScenesFromNotes(user, bookOid)` resolves the book via the meta's `pb2BookObjectId` link (`resolveBookGroupEither`), creates one `olio.pb.scene` per note that has no row yet (match by `sceneIndex`, never by name), and is idempotent. It must **not** go through `PbMigrationUtil.importV1Book` (`POST /migrate-v1`, `PbMigrationUtil.java:99`): that path creates a *new* book and throws 409 when the slug already exists (`:148-152`) — which is every `createFromScenes` book and all 228 chapter books — and derives the slug from the group name (`:111`), which for a series chapter is the chapter title, not the slug (`PictureBookUtil.java:9553-9559`). Expose as `POST /olio/picture-book/{book}/scenes/backfill` (transport-only), invoked by an explicit wizard/edit action; **never from `listScenes` or any GET** — a read path that creates N rows is the `architecture.md` "Read paths must not create" violation, and `listScenes` keeps its find-only note fallback until the backfill has been run; (6) retire note writes once `book.sdConfig` FK (already patched by `setBookSdConfig` S6) covers the last meta-only field. The **Story view** is a new route `/picture-book/v2/:id/story` (ordered scenes × cast chips, pre-render, edit affordances from WP-A2/A3) driven by `/scenes` + `/characters` today and Part C's entities later; the canvas keeps a slim read-only story lane linking each SCENE node to its `olio.pb.scene`.

**Decisions for Stephen:** D1 make `olio.pb.scene` primary and retire notes (recommended); D2 keep the DAG provenance-only (recommended) vs. B2; D3 Story view as its own route (recommended) vs. inside the canvas.

**[R2] Two honest costs of `$flex`, stated so D4 is a real choice:**
- *Read side:* "resolves through the reader" was imprecise. A select returns an `{id, schema}` stub (`StatementUtil.java:803-821`) and `QueryPlan` skips `$flex` fields entirely (`QueryPlan.java:25,245,305`; the workaround is `ChatUtil.java:541-546`). So a Story view listing N scenes × M entities needs a **per-type batched populate** in `PbEntityUtil.populateEntities(List<sceneEntity>)` (group stubs by `entityType`, one `IN` query per type), not a projection on `/scenes`.
- *Write side:* the only existing persisted `$flex` writers are `InteractionExtractor.createInteraction :252-286` and `ChatEventUtil :59-75`, both in `olio/llm`, and both do phase 2 as a raw `RecordUtil.updateRecord` — **that is a PBAC bypass, not a sanctioned pattern** (`architecture.md` has no exemption; `FeatureConfigUtil.java:399` says so explicitly). Rev 1 wrongly proposed copying it. See C4 write discipline and **D4b**.

**D4b spike result (2026-10-01, `TestFlexWritePolicy`, 4/4 on `am7db`, two non-admin users):** the bypass is unnecessary. `$flex` fields are declared `type: "model"` + `foreign: true` + `baseModel: "$flex"`, so `PolicyUtil.getSchemaRules` (`:460-477`) treats them as an ordinary foreign MODEL field (`followReference` defaults true, `FieldSchema.java:65`) and `getForeignPatterns` (`:414-415, :420-433`) builds a READ-object pattern from the linked record's own schema. Measured: `AccessPoint.update(A, interaction{actor = A's charPerson})` → `AUDIT PERMIT`, FK persisted; the same with an **id-only stub** (`{schema, id}`) → PERMIT, FK persisted (so the "stubs without group/org fail policy checks" reason at `MemoryUtil.java:82-83` does not hold — `getForeignPatterns :421-423` populates the stub); `AccessPoint.update(A, interaction{actor = B's charPerson, unreadable by A})` → trace `Add rule for actor` / `Add UPDATE foreign access pattern for olio.interaction.actor` / `Adding 1 dynamic rules` → `AUDIT DENY`, FK unchanged. The raw `RecordUtil.updateRecord` path with the same unreadable record → `updated=true`, FK = B's person. ⇒ **C4 writes `$flex` fields through `AccessPoint` in one phase.** The `olio/llm` two-phase writers are a latent defect (they link records the caller cannot read), noted for Stephen; not in this plan's scope.

**Decision D4:** `$flex` FK (recommended; D4b resolved cleanly — see spike result above) vs. `refModel`+`refObjectId` strings (binding precedent: one-phase write, no PBAC question, but no FK integrity and the same batched-populate cost on read).

**Scene ↔ event:** one `olio.event` per scene, child of the book's chapter event (root → chapter → scenes, per the C1 row); `sceneIndex` on `olio.pb.scene` is the **primary** order; `precedingEvents/subsequentEvents` are **derived** and rebuilt by `reorderScenes`.
