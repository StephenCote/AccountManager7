## Issue 1 — Submitting a full novel manuscript with chapters fails after a ~90 min timeout (FIXED — timeout SOLVED live; B1/B2 FIXED + verified)

**Reported (Stephen, 2026-09-22):** "when submitting a full novel manuscript with chapters it fails
after a 90 min timeout." Direct note: *"clearly you didn't test"* — the chapters/novel path was
claimed working without a real end-to-end run on a full manuscript.

**Symptom:** Submitting a whole-novel manuscript (multiple chapters) does not complete; it fails only
after roughly 90 minutes, i.e. a timeout rather than a fast error.

**Status:** INVESTIGATED (root cause located by code reading; **not reproduced** — a real repro is a
90-minute run). No fix applied yet.

### Root cause (hypothesis, cited): the 90-min limit is a CLIENT poll deadline, not a backend/proxy timeout

The whole-novel submission is already async and server-safe. The "hang ~90 min then fail" is produced
entirely in the Ux poller giving up while the server job is still running.

- **The heavy path is a single async extraction job over the WHOLE manuscript.** Wizard:
  [`pictureBook.js:433`](../AccountManagerUx752/src/workflows/pictureBook.js#L433) `startExtractScenes` →
  `:437` `pollJob`; the request is
  [`sceneExtractor.js:160-161`](../AccountManagerUx752/src/workflows/sceneExtractor.js#L160-L161)
  `POST /rest/olio/picture-book/{workObjectId}/extract-scenes-only?async=true` → `202 {jobId}`
  (`PictureBookService.java` `extractScenesOnly`, async branch). The whole novel is chunked
  (chunkSize 2000 / overlap 200) and looped inside that **one** worker thread.
- **The "chapters" REST path does no extraction.** `POST /olio/picture-book/chapter`
  (`PictureBookService.java:1174` → `PbServiceFacade.createChapter`) is a fast record-create.
  Auto-splitting a novel into chapters (the N-series) is **PLAN-ONLY / not implemented**
  ([`PictureBookSeriesChaptersPlan.md:3`](PictureBookSeriesChaptersPlan.md)). So today a "full novel
  with chapters" is really one giant single-document extraction, not N bounded per-chapter jobs.
- **What fires at ~90 min:** the client constant
  [`sceneExtractor.js:46`](../AccountManagerUx752/src/workflows/sceneExtractor.js#L46)
  `JOB_POLL_DEADLINE_MS = 90 * 60 * 1000`, thrown at
  [`sceneExtractor.js:128-133`](../AccountManagerUx752/src/workflows/sceneExtractor.js#L128-L133)
  ("Timed out waiting for job … after 90 minutes"), surfaced as `extractError` in `pictureBook.js:444`.
  This is the exact 90-minute figure. Its own comment (`:129-130`) says it deliberately does **not**
  cancel the job — the server keeps working and the result stays retained.
- **No server-side 90-min cap.** `AsyncJobRegistry` has only `MAX_CONCURRENT_JOBS=2` and a 30-min
  *completed-result* TTL — no per-job runtime cap. Other timeouts do NOT fire at 90 min: nginx
  `proxy_read_timeout 3600s` (=60 min, `docker/nginx.conf`) applies to the sync path/initial POST, not
  to the fast async polls; per-LLM-call read timeout ~1200s; Jersey read timeout ~360s.
- **The work is genuinely too big for one 90-min window.** A ~300 KB novel ≈ ~165 chunks × ~80–110 s
  ≈ 4–5 h in one unbounded loop. The per-chunk checkpoint (keyed per-DOCUMENT) lets the *server* resume
  across a restart, but does nothing to keep the *client* watching, and does not split the work into
  per-chapter jobs.

### Fix direction (NOT yet done — for triage, not a claim of completion)

1. **Client:** at the poll deadline, don't render a still-running job as a hard error. Detach and offer
   reattach — `reattachExtractJob` already exists (`pictureBook.js:487`), and the job result is retained
   server-side. Raising `JOB_POLL_DEADLINE_MS` alone is a band-aid.
2. **Real fix:** bound the work per chapter — one async job per chapter/range (the N-series work in
   [`PictureBookSeriesChaptersPlan.md`](PictureBookSeriesChaptersPlan.md)), so each finishes well inside
   a sane window and a whole-novel submission becomes a series of bounded jobs rather than one 4–5 h run.

Layer verdict: **client/UX behavior**, not a backend defect — the async REST contract is behaving as
designed. Escalation to the backend is not warranted for the timeout itself.

### Decision (Stephen, 2026-09-22): implement the real per-chapter fix (N-series)

Not the client band-aid. The durable fix is to make a novel submission fan out into **one bounded
async job per chapter/range** so each finishes well inside a sane window — i.e. the N-series in
[`PictureBookSeriesChaptersPlan.md`](PictureBookSeriesChaptersPlan.md) (N1 series+shared world,
N2 chapter linkage + range descriptor + range-aware extraction checkpoint, N3 heading→offset boundary
detection, N4 canvas view states). Issue 1 stays OPEN until a real end-to-end run over a full
manuscript completes without the 90-min client timeout.

**CORRECTION to the plan's status (verified 2026-09-22):** the N-series is **not** plan-only — much of
it is already implemented in the tree despite the plan doc's stale "PLAN ONLY" header. Present today:
`PbSeriesUtil.java`, `PbChapterBoundaryUtil.java`, `models/olio/pb/sourceRangeModel.json`, and a test

`TestPbChapterBookApparelRenderE2E`, `TestPbDetectBoundariesFacade`, `TestPbListSeriesBooks`,

boundary-detect → per-chapter books → one bounded async job per chapter, and to prove it end-to-end.

### Design review (architect, 2026-09-22): APPROVED with binding constraints

Verdict **CHANGES-NEEDED** only because of decision #3 (checkpoint range-awareness) as originally
phrased; the architecture is otherwise sound. Rulings:

1. **`POST /series` — APPROVED.** Legal transport (all logic stays in `PbSeriesUtil.getCreateSeries`).
   Belongs in `PictureBookService` (sibling to `/chapter`, `/series/{id}/books`), NOT `OlioService`.
   `@RolesAllowed({"admin","user"})`, principal via `ServiceUtil.getPrincipalUser`; `getCreateSeries`
   resolves the olio principal internally for its FK/row writes and re-reads as the acting user to
   prove the grant. **Binding: keep it POST-only — never reach `getCreateSeries` from a GET/read
   handler** (architecture.md "Read paths must not create").
2. **Extraction target — Option B (client passes explicit `startOffset`/`endOffset`).** Option A
   (read back `book.sourceRange`) walks into three documented traps: foreign field not auto-populated +
   the `planMost(true)` 100-arg limit on `olio.pb.book`, nested-FK cache staleness, and groupless PBAC
   on the `common.baseLight` sub-record. Option B reuses the offsets the client already holds from
   `detect-boundaries`. **Binding: server-side validate/clamp `0 <= startOffset < endOffset <=
   text.length()` before slicing.**
3. **Checkpoint range-awareness — the core correction.** Setting `checkpoint.startOffset/endOffset` is
   necessary but NOT sufficient. Four call sites, three currently broken:
   - SAVE (`saveExtractCheckpoint` → `progressNoteName` :4487-4496) — fine once fields are set.
   - LOAD (`extractChunkedInternal` :4815-4816 uses the 7-arg no-range overload → reads the BARE note)
     — **must switch to the 9-arg range overload (:4526)**, else resume never finds its own checkpoint
     and every chapter thrashes back to chunk 1.
   - COMPLETION CLEAR (:5125 `clearExtractCheckpointAt` no-range → clears the BARE note) — **must pass
     the range**, else each chapter's suffixed checkpoint is orphaned.
   - `fresh=true` CLEAR (`PictureBookService.java:220` `clearExtractCheckpoint` no-range) — **must
     thread the range**, else a per-chapter fresh re-run discards the wrong checkpoint.
   - Plumbing: `extractChunkedInternal` (:4756) must accept `startOffset/endOffset` params first.
   - **Do NOT fold the range into the `textHash` guard** — ranges are isolated by note NAME and the
     load guard's range-equality check (:4558-4564), which is strictly stronger. The slice is hashed
     after slicing, so different ranges already differ; identical ranges write distinct suffixed notes.
4. **Sequential client-driven fan-out — APPROVED.** Client only sequences existing transport calls +
   polls (orchestration, not business logic). A server-orchestrated single job would re-introduce the
   4–5 h unbounded unit being fixed. **Binding: sequential** (`MAX_CONCURRENT_JOBS=2`, one Ollama).
   Verified non-blockers: `AsyncJobRegistry.submit` keys on random `jobId` not `workObjectId` (per-chapter
   jobs don't collide); async cancel uses each job's own progress token, not the `(user,workObjectId)`
   `PictureBookCancelRegistry`.

**Test requirements (architecture.md verification standard):** new Objects7 overload + range
checkpointing need a two-range same-`workObjectId` resume JUnit test (proves chapter 2 doesn't resume
chapter 1's checkpoint — from REAL extraction, not a hand-built `ExtractCheckpoint`); new `POST /series`
route needs a service unit test. Ollama at 192.168.1.42 is live — extraction paths are testable.

#### Contract verification (2026-09-23) — one confirmed backend defect blocks (1)
